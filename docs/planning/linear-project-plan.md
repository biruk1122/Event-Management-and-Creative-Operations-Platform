# Proposed Linear project plan

## Approval boundary

This document is the Phase 9 proposal. It does not authorize creating Linear records or
implementing product features. After approval, the approved hierarchy and issues will be created
in Linear. Any requested changes will be incorporated before creation.

The product requirements come from the versioned SRS. The technical constraints come from the
approved architecture and the current repository foundation.

## Linear hierarchy

- Initiative: `Event and Creative Operations Platform`
- Project: `Product Delivery - Version 1`
- Project summary: Deliver a secure, responsive connected workspace for company operations while
  preserving the modular-monolith, OpenAPI, PostgreSQL, and real-time boundaries.
- Project lead: repository/product owner
- Delivery model: milestone -> epic parent issue -> small child issues
- Workflow: `Backlog -> Ready -> In Progress -> In Review -> Done`, with `Blocked` and `Canceled`
- Branch format: `feature/<linear-id>-<short-description>`

### Milestones

| Milestone                              | Outcome                                                                                     | Exit condition                                                                         |
| -------------------------------------- | ------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| M0 - Delivery enablement               | Product language, contracts, test harnesses, and shared delivery patterns are ready.        | Subsequent feature issues can be implemented without inventing cross-cutting patterns. |
| M1 - Identity and organization         | Authentication, configurable RBAC, users, departments, and teams work end to end.           | Authorized users can sign in and organizational access is enforced.                    |
| M2 - Connected core operations         | Workspace ownership, files, events, projects, and tasks work as connected modules.          | An event or project can coordinate teams, tasks, files, progress, and activity.        |
| M3 - Discuss and notifications         | Durable messaging, channels, real-time delivery, mentions, and notifications work securely. | Authorized users communicate and reconcile missed state after reconnecting.            |
| M4 - Planning and scheduling           | Calendar, meetings, personal schedules, To-Do, and reminders work together.                 | A user can answer what they need to do and attend today.                               |
| M5 - Creative business operations      | Talent, production, promotion, and marketing workflows use the connected workspace.         | Specialized departments can manage their operational work end to end.                  |
| M6 - Reporting and dashboards          | Reports, management analytics, and employee dashboards use authoritative operational data.  | Roles receive accurate actionable summaries without unrestricted data exposure.        |
| M7 - Security, performance, and launch | The system is hardened, observable, recoverable, documented, and deployable.                | Production readiness review and release acceptance pass.                               |
| M8 - Optional integrations and AI      | Explicitly approved email, Meet, and Gemini extensions are delivered safely.                | Each optional capability passes a separate value, privacy, and operating-cost gate.    |

## Issue contract

Every created Linear issue will contain these headings:

1. `Description and objective`
2. `Scope` with explicit in-scope and out-of-scope items
3. `Technical requirements`
4. `Acceptance criteria` as verifiable checkboxes
5. `Dependencies` using Linear blocking relationships
6. `Priority`
7. `Estimated implementation complexity`
8. `Areas` using the labels below

No issue may enter `Ready` until its dependencies are done and its acceptance criteria are
testable. No issue may enter `Done` until implementation notes, verification evidence, and any
contract or migration impact are recorded.

### Priority, estimate, and area labels

- Priorities: `P0 Critical`, `P1 High`, `P2 Medium`, `P3 Low`
- Complexity: `XS (1)`, `S (2)`, `M (3)`, `L (5)`, `XL (8)`; work estimated above 8 must be split
- Areas: `frontend`, `ui-ux`, `backend`, `database`, `api-contract`, `realtime`, `testing`,
  `security`, `infrastructure`, `documentation`, `observability`, `performance`
- Product labels: `identity`, `organization`, `workspace`, `files`, `events`, `projects`, `tasks`,
  `discuss`, `notifications`, `calendar`, `meetings`, `todo`, `talent`, `production`, `promotion`,
  `marketing`, `reporting`, `dashboard`, `integration`, `ai`

## Dependency order

```text
M0 Delivery enablement
  -> M1 Identity and organization
      -> M2 Connected core operations
          -> M3 Discuss and notifications
          -> M4 Planning and scheduling
              -> M5 Creative business operations
                  -> M6 Reporting and dashboards
                      -> M7 Security, performance, and launch
                          -> M8 Optional integrations and AI (separately approved)
```

M3 and the independent portions of M4 may run in parallel after their stated dependencies are
complete. M5 epics may also overlap when their shared workspace, task, file, calendar, and discuss
contracts are stable. Linear blocking relations, not milestone numbers alone, determine readiness.

## Linear creation sequence after approval

1. Confirm the target Linear workspace and team.
2. Create the initiative, project, milestones, labels, and workflow mapping where permissions
   allow; reuse existing equivalents rather than creating duplicates.
3. Create epic parent issues.
4. Create actionable issues with the required body sections and metadata.
5. Add parent-child and blocking relationships in dependency order.
6. Audit counts, titles, priorities, estimates, labels, descriptions, acceptance criteria, and
   dependencies against this approved plan.
