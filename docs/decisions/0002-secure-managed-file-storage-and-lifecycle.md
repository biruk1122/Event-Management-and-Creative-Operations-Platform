# 0002 - Secure managed-file storage and lifecycle

- Status: Accepted
- Date: 2026-09-08
- Deciders: Platform architecture
- Linear issue: EVE-36 (EN-08)
- Supersedes: none
- Superseded by: none

## Context

The SRS requires secure file uploads and collaboration attachments. It identifies task
attachments, message attachments, and files in event and project workspaces, but it does not
specify a storage provider, public URL model, retention period, or upload safety controls. It also
lists `fileName`, `fileUrl`, and `fileType` on task and message attachment examples; those are
not sufficient contracts for secure object storage.

The technical architecture reserves S3-compatible storage for a future implementation and keeps
MinIO as a development-only extension point. It requires the API to remain the boundary to
PostgreSQL and public contracts. The product vocabulary defines a managed file as metadata
governed by authenticated ownership, authorization, storage, and retention rules, and explicitly
states that raw storage references are not public contracts. Its OD-12 requires these rules before
attachments are implemented.

EVE-33 additionally reserves `managed_file.downloaded` for files classified sensitive by this
decision and requires `managed_file.deleted` to be audited.

## Decision

### 1. Managed files are private, backend-governed resources

- A managed file has authoritative metadata in PostgreSQL and opaque object bytes in a private,
  S3-compatible bucket. The metadata schema, migrations, API routes, and attachment association
  tables belong to FIL-01 and later FIL issues.
- Object keys are generated by the API from the managed-file UUID and server randomness. They do
  not contain an original filename, user id, parent record id, or other business data. A storage
  key, bucket name, provider URL, and presigned URL are infrastructure details and never appear in
  normal API responses, persisted attachment references, logs, or activity history.
- Neither the browser nor any product role receives bucket credentials, object-list permission, a
  public ACL, or a permanent file URL. A CDN may only be introduced by a later decision that
  preserves per-request authorization; it cannot make the bucket public.
- Each file is linked through an explicit approved parent or association record. Generic
  `entityType/entityId` attachment references are prohibited. A file with no completed approved
  link is not available for download.

### 2. Storage-provider and development boundary

- Production uses an S3-compatible object-storage API. The provider, region, encryption-key
  ownership, disaster-recovery configuration, and operational credentials are deployment concerns
  and are not selected by this decision.
- When FIL begins, local development uses a private MinIO service with the same S3 API contract.
  MinIO is not added to Docker or production configuration by EVE-36. Development configuration
  uses non-production credentials supplied through the environment; repository defaults, browser
  bundles, fixtures, and logs never contain storage secrets.
- Server-side storage access is confined to the API's file infrastructure adapter. It receives the
  least privileges necessary to create, inspect, issue short-lived grants for, and delete objects
  under the managed-file prefix. Database authorization always happens before that adapter is
  called.

### 3. Upload contract and safety boundary

The API owns the upload lifecycle. A client cannot create an attachment merely by putting an object
in storage.

1. The client requests an upload intent with its approved parent context, original filename,
   declared media type, and byte length. The API authenticates the active user and authorizes the
   parent mutation. For a task, this includes `task.attachment.create` and the task's resolved
   scope; future parent modules must map their own create/edit permission at their application
   boundary.
2. The API validates the declared name, type, and size, creates a pending managed-file record, and
   issues a one-object presigned POST upload policy. The policy enforces the exact opaque key,
   expected media type, and a `content-length-range` from 1 byte through 10 MiB before storage
   accepts the bytes. It expires in 10 minutes and cannot list, read, overwrite another key, choose
   an ACL, or supply arbitrary object metadata.
3. The client uploads directly to the exact opaque key, then asks the API to finalize. The API uses
   object metadata and a bounded content inspection to verify the received size, detected type,
   and safety requirements. A failed or expired intent never creates a usable attachment.
4. Only after validation, malware-scan policy, and explicit parent-link authorization succeed does
   the API mark the file available and create the association transactionally. The browser must
   treat a file as unavailable until that response succeeds.

The initial permitted file types are PDF documents; JPEG, PNG, and WebP images; plain text and
CSV; and OOXML Word, Excel, and PowerPoint documents (`.docx`, `.xlsx`, `.pptx`). The initial
maximum is 10 MiB per object. The signed policy enforces that limit before upload, and finalization
rechecks the received size as defense in depth. Multipart/resumable uploads, archives, audio/video,
SVG, HTML, JavaScript, executables, macro-enabled Office files, and every unrecognized type are out
of scope and rejected until separately approved.

The API does not trust an extension or client-supplied media type. It normalizes the filename for
display only, rejects path separators, control characters, empty names, and names over 255 UTF-8
bytes, and never uses it as a storage key. It verifies allowed types from bounded byte signatures
and format structure before availability. OOXML files must be non-encrypted and satisfy a bounded
ZIP inspection: no more than 1,000 entries and no more than 100 MiB total uncompressed content.
Mismatched, malformed, encrypted, or unsafe content is rejected and scheduled for deletion.

The file adapter exposes a scanner interface that returns `clean`, `infected`, or `unavailable`.
Production finalization requires a `clean` result before a file is available. The development
adapter may use a clearly marked test scanner only; it must not silently become a production
fallback. Scanner unavailability leaves a file unavailable and returns a recoverable service
error, without changing its parent record.

### 4. Download contract and authorization

- A download begins with an API request for a managed-file id, not a storage URL. On every request,
  the API checks that the file is available, resolves its explicit parent relationship, and applies
  the same server-side read/scope policy that permits viewing that parent. Direct, guessed, removed,
  quarantined, expired, or unauthorized file ids return a non-enumerating not-found/denied result.
- On success, the API issues a single-object presigned `GET` grant that expires in five minutes.
  The response uses the verified media type, a sanitized attachment `Content-Disposition` filename,
  and private, no-store cache behavior. It does not grant object listing or reuse after expiry.
- Every managed file is initially classified as sensitive operational content because the SRS has
  no lower-risk file classification and attachments may carry private conversations, task work, or
  workspace material. Each successful download therefore writes the durable
  `managed_file.downloaded` audit record required by ADR 0001, with the actor, file id, explicit
  parent context, request id, and outcome but no storage URL, filename, or file content. The audit
  record commits before the signed grant is returned.

### 5. Retention, deletion, and orphan cleanup

- A pending upload intent expires after 24 hours. Its metadata and any object at its opaque key are
  deleted by cleanup and cannot be finalized afterwards.
- A file that was uploaded but never linked to an approved parent is an orphan candidate. Cleanup
  deletes it seven days after it became eligible, allowing transient finalization failures to be
  retried without accumulating durable junk.
- Removing the final approved association makes the file unavailable immediately. The metadata and
  bytes remain in a 30-day recovery window, then cleanup permanently deletes the object and its
  metadata. A valid reattachment during that window cancels deletion only after fresh
  authorization; after permanent deletion, re-upload is required.
- Attached files remain while their parent relationship remains valid. A future parent module that
  implements deletion, archival, or retention must explicitly call this lifecycle and may not
  bypass it with a direct storage delete. This decision does not invent a retention policy for the
  parent business records themselves.
- A scheduled, idempotent cleanup worker reconciles expired intents, orphan candidates, detached
  files, and storage objects under the managed-file prefix. It treats storage deletion as
  retryable, records safe operational diagnostics, and never scans or deletes outside that prefix.
  A missing object marks its metadata unavailable for repair; it is not silently served.
- Every permanent deletion creates the durable `managed_file.deleted` audit record from ADR 0001.
  A cleanup deletion records `system` as its actor. Cleanup records do not include raw filenames,
  object paths, file bytes, tokens, or signed URLs in logs or audit metadata.

## Consequences

### Positive

- Browser transfers can avoid routing file bytes through the API while authorization, metadata,
  inspection, audit, and lifecycle ownership remain server-controlled.
- The initial allow-list and bounded inspection substantially reduce executable, active-content,
  and compressed-content risk before later hardening work.
- Short-lived grants and explicit parent links protect files from public-bucket exposure and
  insecure generic relationships.
- Defined expiry and cleanup paths prevent abandoned uploads and removed attachments from becoming
  permanent storage leaks.

### Trade-offs

- Presigned transfer requires a multi-step client workflow and explicit pending/unavailable UI
  states.
- Validating and scanning after upload may consume storage briefly for rejected content; cleanup
  must be monitored.
- Auditing all downloads increases audit volume. This is intentional until an approved content
  classification model can safely distinguish lower-risk files.
- The 10 MiB limit and excluded media/archive formats are deliberately conservative. A later issue
  may supersede this ADR with evidence-based requirements, safe processing limits, and performance
  validation.
